# Evaluation of GPT-5-Codex, GPT-5, Claude Sonnet 4.5, S100, and S40 on Bug-related – Functional Bug Detection, Correction, and Optimization

This workspace demonstrates a functional bug scenario alongside its corrected implementation. Project A reproduces the faulty behaviour, while Project B delivers the optimized fix. Both projects share the same nested payload scoring problem: compute a weighted insight score from arbitrarily nested event payloads that may contain malformed values.

## Test Scenario
- **Input format:** List of event dictionaries, each containing a `type`, optional numeric `value`, and optional nested `children`. Weight mappings provide per-type multipliers.
- **Output format:** Single floating-point score representing the weighted sum of all normalized values.
- **Bug type:** Project A resets its accumulator when descending into nested children and mishandles list/dict values, producing incorrect totals and scaling poorly.
- **Improvement goal:** Project B preserves partial sums, fully normalizes arbitrarily nested collections, and caches weight lookups to reduce redundant dictionary access.

## Repository Structure
- `Project_A_Faulty/`: Original implementation, requirements, setup script, tests, execution driver, logs, and timing stub.
- `Project_B_Optimized/`: Corrected implementation with the same supporting assets.
- `test_data.json`: Five structured evaluation cases (normal, edge, malformed, vulnerability, and deeply nested).
- `run_all.sh`: Orchestrates both projects and emits `compare_report.md`.
- `compare_report.md`: Side-by-side comparison placeholder (regenerated by `run_all.sh`).

## Running the Projects
1. Ensure a Python 3.10+ interpreter and a POSIX shell (e.g., Git Bash on Windows) are available.
2. (Optional) Execute `Project_A_Faulty/setup_original.sh` and `Project_B_Optimized/setup_optimized.sh` to create isolated environments.
3. Run `Project_A_Faulty/run_original.sh` to capture the failing pytest output and timing data for the faulty version.
4. Run `Project_B_Optimized/run_optimized.sh` to validate the fixed implementation.
5. Execute `./run_all.sh` from the repository root for a one-click workflow that runs both projects and regenerates `compare_report.md`.

`run_all.sh` reads the produced logs and recomputes accuracy metrics against `test_data.json`, yielding a reproducible comparison of correctness, timing, and stability.

## Reproducibility and Environment
- Each project supplies its own `requirements_*.txt` file pinning pytest for consistent testing.
- Setup scripts create project-specific virtual environments (`.venv_original` and `.venv_optimized`).
- Tests rely solely on files tracked in this repository, enabling deterministic runs across machines.

## Limitations
- The shell scripts assume a POSIX-compatible environment. Windows users should rely on Git Bash or WSL.
- Timing numbers in `time_*.txt` are coarse wall-clock measurements captured by the run scripts; they should be treated as approximate.
- No Dockerfiles are included; use the provided virtual environments for isolation.
